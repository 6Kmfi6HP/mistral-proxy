## 1. How Function Calling Works in the Conversations API

### Overview

The Mistral Conversations API (`/v1/conversations`) is a **stateful conversation API** that manages conversation history server-side. Function calling works differently from the Chat Completions API:

- **Chat Completions API** (`/v1/chat/completions`): Uses `messages` with roles (system/user/assistant/tool). Tool calls appear as `tool_calls` on assistant messages. Tool results are sent as `tool` role messages with `tool_call_id`. The client manages history.

- **Conversations API** (`/v1/conversations`): Uses **entries** — a flat list of typed entries. The server manages conversation history. Function calls and results are first-class entry types (`function.call` and `function.result`), not embedded in messages.

### Flow

1. **Developer defines tools** (function tools + built-in tools) in the `tools` parameter
2. **User sends inputs** (a string or array of entries) to `POST /v1/conversations` or `POST /v1/conversations/{conversation_id}`
3. **Model generates function call** — the server returns a `FunctionCallEntry` (type: `function.call`) in the `outputs` array
4. **Developer executes the function** locally and sends back a `FunctionResultEntry` (type: `function.result`) in the next request's `inputs`
5. **Model generates final answer** based on the function result

### Tool Choice

Via `completion_args.tool_choice`:
- `"auto"` (default): Model decides whether to use a tool
- `"any"` / `"required"`: Forces tool use
- `"none"`: Prevents tool use
- `{"type": "function", "function": {"name": "my_function"}}`: Forces a specific function

### Parallel Tool Calling

In the Chat Completions API, `parallel_tool_calls` (boolean, default `true`) controls whether the model can call multiple tools in one response.

In the Conversations API, the `CompletionArgs` schema does NOT include `parallel_tool_calls` — the model decides this automatically.

### Tool Confirmation

The Conversations API adds a **tool confirmation** mechanism (`tool_confirmations` on append, `confirmation_status` on function call entries):
- `ToolCallConfirmation`: `{tool_call_id: string, confirmation: "allow" | "deny"}`
- Function call entries have a `confirmation_status` field: `"pending" | "allowed" | "denied"`
- The `ToolConfiguration` on built-in tools can specify `requires_confirmation` (array of tool names)

## 2. The `function.call` Entry Type (FunctionCallEntry)

This entry represents a function call generated by the model. It appears in `outputs` (server-generated) and can also appear in `inputs` (when replaying/reconstructing history).

### Schema (OpenAPI wire format — snake_case)

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `object` | string (const: `"entry"`) | No (default) | Always `"entry"` |
| `type` | string (const: `"function.call"`) | No (default) | Entry type discriminator |
| `created_at` | string (date-time) | No | When the entry was created |
| `completed_at` | string (date-time) \| null | No | When completed |
| `agent_id` | string \| null | No | Agent that generated this call (if using agents) |
| `model` | string \| null | No | Model that generated this call |
| `id` | string | No | Unique entry ID |
| `tool_call_id` | string | **Yes** | ID to correlate with the function result |
| `name` | string | **Yes** | Name of the function being called |
| `arguments` | object \| string (FunctionCallEntryArguments) | **Yes** | Function arguments — can be a JSON object or a string |
| `confirmation_status` | `"pending"` \| `"allowed"` \| `"denied"` \| null | No | Whether this tool call requires/has confirmation |

### JSON Example

```json
{
  "object": "entry",
  "type": "function.call",
  "id": "call_abc123",
  "tool_call_id": "call_abc123",
  "name": "get_payment_status",
  "arguments": {"transaction_id": "T1001"},
  "created_at": "2025-01-15T10:30:00Z",
  "completed_at": "2025-01-15T10:30:00Z",
  "confirmation_status": null
}
```

### Key differences from Chat Completions `tool_calls`

In Chat Completions, tool calls are nested inside an assistant message:
```json
{"role": "assistant", "tool_calls": [{"id": "...", "function": {"name": "...", "arguments": "..."}}]}
```

In Conversations API, each function call is a **standalone entry** at the top level of the conversation history, not nested inside a message.

## 3. The `function.result` Entry Type (FunctionResultEntry)

This entry represents the result of executing a function. It is sent by the developer in `inputs`.

### Schema

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `object` | string (const: `"entry"`) | No (default) | Always `"entry"` |
| `type` | string (const: `"function.result"`) | No (default) | Entry type discriminator |
| `created_at` | string (date-time) | No | When created |
| `completed_at` | string (date-time) \| null | No | When completed |
| `id` | string | No | Unique entry ID |
| `tool_call_id` | string | **Yes** | Must match the `tool_call_id` of the corresponding `function.call` |
| `result` | string | **Yes** | The function result as a string (typically JSON-serialized) |

### JSON Example

```json
{
  "object": "entry",
  "type": "function.result",
  "tool_call_id": "call_abc123",
  "result": "Paid"
}
```

### Key differences from Chat Completions `tool` messages

In Chat Completions, tool results are sent as messages with role `"tool"`:
```json
{"role": "tool", "content": "Paid", "tool_call_id": "call_abc123"}
```

In Conversations API, tool results are standalone entries of type `function.result`.

## 4. Tool Definitions: OpenAI vs Mistral Formats

### Function Tool Definition

Both Chat Completions and Conversations API use the **same tool definition format**:

```json
{
  "type": "function",
  "function": {
    "name": "get_payment_status",
    "description": "Get payment status by transaction ID",
    "parameters": {
      "type": "object",
      "properties": {
        "transaction_id": {"type": "string"}
      },
      "required": ["transaction_id"]
    }
  }
}
```

### Schema: `FunctionTool` (Conversations API) / `Tool` (Chat Completions API)

Both are structurally identical:

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `type` | `"function"` (const/enum) | No (default) | Tool type discriminator |
| `function` | `Function` object | **Yes** | Function definition |

### `Function` Object

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `name` | string | **Yes** | Function name |
| `description` | string | No (default: `""`) | Function description |
| `strict` | boolean | No (default: `false`) | Strict mode for structured outputs |
| `parameters` | object (JSON Schema) | **Yes** | Function parameter schema |

### Comparison with OpenAI

Mistral's tool definition format is **nearly identical to OpenAI's**:
- Same `{"type": "function", "function": {...}}` wrapper
- Same `name`, `description`, `parameters` fields
- `strict` field exists in both (Mistral supports structured outputs)
- OpenAI uses `parameters` as a JSON Schema object; Mistral does the same with `additionalProperties: true`

### Built-in Tools (Conversations API only)

The Conversations API supports additional tool types beyond `function`:

| Tool Type | Schema | Description |
|-----------|--------|-------------|
| `function` | `FunctionTool` | Custom function (execution on client) |
| `web_search` | `WebSearchTool` | Built-in web search (server-side execution) |
| `web_search_premium` | `WebSearchPremiumTool` | Premium web search |
| `code_interpreter` | `CodeInterpreterTool` | Built-in code execution (server-side) |
| `image_generation` | `ImageGenerationTool` | Built-in image generation |
| `document_library` | `DocumentLibraryTool` | RAG over uploaded document libraries |
| `connector` | `CustomConnector` | MCP server connector |

All built-in tools share an optional `tool_configuration` with:
- `exclude`: array of strings (tool names to exclude)
- `include`: array of strings (tool names to include)
- `requires_confirmation`: array of strings (tool names requiring user confirmation)

### Important: Built-in tools in Chat Completions

Per the docs: `web_search`, `web_search_premium`, and `code_interpreter` are **NOT supported** in Chat Completions API (`/v1/chat/completions`). They only work with Conversations API and Agents API. However, `image_generation` and `document_library` ARE supported in Chat Completions.

## 5. Streaming Events for Function Calls

### SSE Event Types (ConversationEvents)

When streaming (`stream: true`), the Conversations API emits Server-Sent Events. Each event has:
```json
{"event": "<sse_type>", "data": {<event-specific data>}}
```

### All SSE Event Types (SSETypes enum)

| Event Type | Data Schema | Description |
|------------|-------------|-------------|
| `conversation.response.started` | `ResponseStartedEvent` | Stream started, includes `conversation_id` |
| `conversation.response.done` | `ResponseDoneEvent` | Stream completed, includes `usage` |
| `conversation.response.error` | `ResponseErrorEvent` | Stream error, includes `message` and `code` |
| `message.output.delta` | `MessageOutputEvent` | Incremental text/content output |
| `tool.execution.started` | `ToolExecutionStartedEvent` | Built-in tool execution started |
| `tool.execution.delta` | `ToolExecutionDeltaEvent` | Built-in tool execution progress |
| `tool.execution.done` | `ToolExecutionDoneEvent` | Built-in tool execution completed |
| `agent.handoff.started` | `AgentHandoffStartedEvent` | Agent handoff initiated |
| `agent.handoff.done` | `AgentHandoffDoneEvent` | Agent handoff completed |
| `function.call.delta` | `FunctionCallEvent` | Function call delta (incremental) |

### `FunctionCallEvent` (for `function.call.delta`)

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `type` | string (const: `"function.call.delta"`) | No | `"function.call.delta"` | Event type |
| `created_at` | string (date-time) | No | — | Timestamp |
| `output_index` | integer | No | `0` | Index of this output in the outputs array |
| `id` | string | **Yes** | — | Unique ID for this function call |
| `model` | string \| null | No | `null` | Model name |
| `agent_id` | string \| null | No | `null` | Agent ID (if using agents) |
| `name` | string | **Yes** | — | Function name |
| `tool_call_id` | string | **Yes** | — | Tool call correlation ID |
| `arguments` | string | **Yes** | — | Function arguments (string, accumulated via deltas) |
| `confirmation_status` | `"pending"` \| `"allowed"` \| `"denied"` \| null | No | `null` | Confirmation status |

**Important**: There is only `function.call.delta` — no separate `function.call.done` event. The function call is considered complete when the next event arrives or `conversation.response.done` fires. The `arguments` field is a string that accumulates across deltas.

### SSE Stream Format

The streaming response is `text/event-stream`. Each SSE message has:
```
event: <sse_type>
data: <json>
```

### Comparison: Chat Completions Streaming

In Chat Completions streaming, tool calls come as deltas on `DeltaMessage.tool_calls`:
```json
{"choices": [{"delta": {"tool_calls": [{"index": 0, "id": "call_xxx", "function": {"name": "fn", "arguments": "{}"}}]}}]}
```
Arguments are accumulated across deltas. The `finish_reason` becomes `"tool_calls"` when done.

In Conversations API streaming, function calls come as dedicated `function.call.delta` events with their own `type`, `name`, `tool_call_id`, and `arguments` fields.

## 6. Built-in Tools: `web_search`, `code_interpreter` — Result Representation

### `tool.execution` Entries (ToolExecutionEntry)

Built-in tools execute **server-side**. Their execution and results are represented as `ToolExecutionEntry` entries (type: `"tool.execution"`).

### Schema: `ToolExecutionEntry`

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `object` | string (const: `"entry"`) | No (default) | Always `"entry"` |
| `type` | string (const: `"tool.execution"`) | No (default) | Entry type |
| `created_at` | string (date-time) | No | When created |
| `completed_at` | string (date-time) \| null | No | When completed |
| `agent_id` | string \| null | No | Agent ID |
| `model` | string \| null | No | Model |
| `id` | string | No | Unique entry ID |
| `name` | `BuiltInConnectors` enum \| string | **Yes** | Tool name (e.g., `"web_search"`, `"code_interpreter"`) |
| `arguments` | string | **Yes** | Tool arguments as string (JSON) |
| `info` | `ToolExecutionInfo` (open object) | No | Execution result info |

### `BuiltInConnectors` Enum

```
"web_search" | "web_search_premium" | "code_interpreter" | "image_generation" | "document_library"
```

### `ToolExecutionInfo`

This is an open object (`additionalProperties: true`) with no fixed schema — the content depends on the tool.

### How Results Appear in Messages

Tool execution results are also reflected in the assistant's `MessageOutputEntry.content` as content chunks:

1. **`ToolReferenceChunk`** (type: `"tool_reference"`): References a tool result with metadata
   - `tool`: tool name (e.g., `"web_search"`)
   - `title`: title of the reference (e.g., web page title)
   - `url`: URL of the source (nullable)
   - `favicon`: favicon URL (nullable)
   - `description`: description (nullable)

2. **`ToolFileChunk`** (type: `"tool_file"`): References a file produced by a tool
   - `tool`: tool name
   - `file_id`: file ID
   - `file_name`: filename (nullable)
   - `file_type`: file type (nullable)

3. **`TextChunk`** (type: `"text"`): Regular text content

### Example: web_search Result in Message Output

From the docs example, a web_search result appears as:
```python
content = [
    TextChunk(text="The current US bank interest rate is 4.50 percent", type="text"),
    ToolReferenceChunk(
        tool="web_search",
        title="United States Fed Funds Interest Rate",
        type="tool_reference",
        url="https://tradingeconomics.com/united-states/interest-rate"
    ),
    TextChunk(text=".\n\nI will now handoff...", type="text")
]
```

### Example: code_interpreter Result

Code interpreter results appear as:
- `ToolExecutionEntry` with `name: "code_interpreter"` and arguments containing the code
- `ToolFileChunk` in message content for any generated files (plots, etc.)
- The `info` field on the `ToolExecutionEntry` / `ToolExecutionDoneEvent` contains execution results

## 7. Agent Handoff

### What is `agent.handoff`?

Agent handoff is a mechanism in Mistral's Agents API that allows one agent to **transfer the conversation to another agent** mid-conversation. This enables building agentic workflows where specialized agents collaborate.

### How Handoffs Work

1. **Create agents** with specific tools and capabilities
2. **Define handoffs** on each agent: `agent.update(handoffs=[other_agent_id, ...])`
3. **Start a conversation** with the first agent
4. When the agent determines another agent should handle the request, it triggers a handoff
5. The conversation continues with the new agent

### `AgentHandoffEntry` Schema

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `object` | string (const: `"entry"`) | No (default) | Always `"entry"` |
| `type` | string (const: `"agent.handoff"`) | No (default) | Entry type |
| `created_at` | string (date-time) | No | When created |
| `completed_at` | string (date-time) \| null | No | When completed |
| `id` | string | No | Unique handoff ID |
| `previous_agent_id` | string | **Yes** | ID of the agent handing off |
| `previous_agent_name` | string | **Yes** | Name of the agent handing off |
| `next_agent_id` | string | **Yes** | ID of the receiving agent |
| `next_agent_name` | string | **Yes** | Name of the receiving agent |

### `handoff_execution` Parameter

Available on `POST /v1/conversations` and `POST /v1/conversations/{conversation_id}`:

| Value | Description |
|-------|-------------|
| `"server"` (default) | Handoffs run automatically on Mistral's servers. The full chain executes and results are returned. |
| `"client"` | When a handoff is triggered, the response returns immediately with the `AgentHandoffEntry`. The client must handle the handoff by continuing the conversation with the target agent. |

### When Does a Handoff Happen?

- An agent decides to hand off based on its instructions and the user's request
- The agent's `handoffs` list defines which agents it can hand off to
- There is **no limit** to the number of chained handoffs
- Example flow: `finance_agent` → (handoff) → `websearch_agent` → (uses web_search tool) → (handoff) → `calculator_agent` → (returns result)

### Handoff in Outputs

`AgentHandoffEntry` appears in the `outputs` array of a `ConversationResponse`, alongside `MessageOutputEntry`, `ToolExecutionEntry`, and `FunctionCallEntry`.

In streaming, handoffs emit `agent.handoff.started` and `agent.handoff.done` events.

## 8. Differences Between Conversations API and Chat Completions API Function Calling

### Architecture

| Aspect | Chat Completions | Conversations API |
|--------|-----------------|-------------------|
| Endpoint | `POST /v1/chat/completions` | `POST /v1/conversations` / `POST /v1/conversations/{id}` |
| State | Stateless (client manages history) | Stateful (server manages history) |
| Input format | `messages` array (role-based) | `inputs` (string or array of entries) |
| Tool calls | `tool_calls` on assistant messages | Standalone `function.call` entries |
| Tool results | `tool` role messages | Standalone `function.result` entries |

### Tool Definitions

Both use the same `{"type": "function", "function": {...}}` format. The Conversations API also supports built-in tools (`web_search`, `code_interpreter`, etc.) directly in the `tools` parameter.

### Streaming

| Aspect | Chat Completions | Conversations API |
|--------|-----------------|-------------------|
| Format | SSE with `data: {json}` chunks | SSE with `event` + `data` |
| Tool call deltas | `delta.tool_calls[].function.arguments` | Dedicated `function.call.delta` events |
| Completion signal | `finish_reason: "tool_calls"` | `conversation.response.done` event |
| Built-in tool events | N/A (not supported for web_search/code_interpreter) | `tool.execution.started/delta/done` events |

### Parallel Tool Calling

- Chat Completions: `parallel_tool_calls` boolean parameter (default `true`)
- Conversations API: Not exposed as a parameter; model decides automatically

### Built-in Tools

- Chat Completions: `image_generation` and `document_library` supported; `web_search`, `web_search_premium`, `code_interpreter` NOT supported
- Conversations API: All built-in tools supported

### Tool Confirmation

- Chat Completions: No confirmation mechanism
- Conversations API: `tool_confirmations` on append requests, `confirmation_status` on function call entries, `requires_confirmation` in tool configuration

### Agent Features

- Chat Completions: No agent support, no handoffs
- Conversations API: Full agent support, `agent_id` parameter, `agent.handoff` entries, `handoff_execution` parameter

### Entry Types Summary (Conversations API only)

| Entry Type | Direction | Description |
|------------|-----------|-------------|
| `message.input` | Input | User/assistant message (role: user or assistant) |
| `message.output` | Output | Assistant message generated by model |
| `function.call` | Output (model) / Input (replay) | Model requests function execution |
| `function.result` | Input (developer) | Developer provides function result |
| `tool.execution` | Output (server) | Built-in tool executed server-side |
| `agent.handoff` | Output (server) | Conversation handed to another agent |

### Response Format

**Chat Completions non-streaming response:**
```json
{
  "id": "...",
  "choices": [{
    "index": 0,
    "message": {
      "role": "assistant",
      "content": null,
      "tool_calls": [{"id": "...", "function": {"name": "...", "arguments": "..."}}]
    },
    "finish_reason": "tool_calls"
  }],
  "usage": {...}
}
```

**Conversations API non-streaming response:**
```json
{
  "object": "conversation.response",
  "conversation_id": "...",
  "outputs": [
    {
      "object": "entry",
      "type": "function.call",
      "id": "...",
      "tool_call_id": "...",
      "name": "...",
      "arguments": "..."
    }
  ],
  "usage": {"prompt_tokens": 0, "completion_tokens": 0, "total_tokens": 0}
}
```

## 9. Conversation API Endpoints

| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | `/v1/conversations` | List all conversations |
| POST | `/v1/conversations` | Create conversation + append entries (non-streaming) |
| GET | `/v1/conversations/{id}` | Get conversation info |
| POST | `/v1/conversations/{id}` | Append entries to conversation (non-streaming) |

| POST | `/v1/conversations/{id}#stream` | Append entries (streaming) |

## 10. Content Chunk Types

### Input Content Chunks (MessageInputContentChunks)

- `TextChunk` — `{"type": "text", "text": "..."}`
- `ImageURLChunk` — `{"type": "image_url", "image_url": "..."}`
- `ToolFileChunk` — `{"type": "tool_file", "tool": "...", "file_id": "..."}`
- `DocumentURLChunk` — `{"type": "document_url", "document_url": "..."}`
- `ThinkChunk` — `{"type": "thinking", "thinking": [...], "signature": "...", "closed": true}`

### Output Content Chunks (MessageOutputContentChunks)

All input chunk types plus:
- `ToolReferenceChunk` — `{"type": "tool_reference", "tool": "...", "title": "...", "url": "...", "favicon": "...", "description": "..."}`

### ThinkChunk (Reasoning)

Contains `thinking` (array of TextChunk/ToolReferenceChunk/ReferenceChunk), optional `signature` for replay, and `closed` boolean (for prefixing).
